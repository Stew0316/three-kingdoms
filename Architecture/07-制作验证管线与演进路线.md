# 制作、验证管线与演进路线

状态：提案  
目标：让架构最终转化为可重复生产内容的能力，而不只是一组类图。

## 1. 技能制作管线

```text
技能意图
→ 机制拆解
→ SkillDefinition
→ 内容校验
→ SkillSandbox
→ 玩家/Boss 适配
→ 动画、VFX、音效
→ AI 使用测试
→ 自动战斗测试
→ 平衡记录
→ 加入正式内容包
```

### 1.1 机制拆解表

每个技能先回答：

- 输入和目标是什么？
- 前摇、提交点、有效期、后摇分别多久？
- 消耗和 CD 在何时提交？
- 是否允许移动、转向、取消和被打断？
- 使用哪些现有效果积木？
- 是否需要新的底层机制？
- 如何命中和去重？
- AI 如何判断使用时机？
- 玩家如何看懂前摇和危险范围？
- 死亡、换图和目标失效时如何清理？

规则：一个新技能最多引入一个尚未验证的底层机制。

### 1.2 SkillSandbox

技能沙盒至少提供：

- 选择释放者和目标。
- 调整距离、朝向和目标数量。
- 重复释放。
- 显示 CastId、阶段、CD、资源和命中集合。
- 开关碰撞形状和范围显示。
- 应用眩晕、沉默、死亡和换图模拟。
- 测试不同帧率、暂停和动作倍率。
- 导出一段结构化战斗日志。

## 2. 地图制作管线

```text
纸面路线与功能目标
→ 灰盒
→ Entrance 和出口连通
→ 碰撞与导航
→ 交互、遭遇和剧情触发
→ 美术铺设
→ 环境音和前景特效
→ MapValidator
→ 跑图、重进和读档测试
```

灰盒阶段先验证：

- 路线长度。
- 视野和转折。
- 战斗空间。
- 捷径和回环。
- 出入口辨识度。
- 玩家是否容易迷路。

正式美术不能用来掩盖路线、碰撞和战斗空间问题。

## 3. 美术和 VFX 管线

```text
风格样板
→ 尺寸、透视和朝向约束
→ 原始素材
→ 切帧或图集
→ Godot 导入预设
→ 材质与 Shader
→ Gameplay Cue 绑定
→ 640×360 实机检查
→ 性能档位
→ 正式内容登记
```

交付检查：

- 命名、尺寸和透明背景正确。
- 原点和角色脚底基准一致。
- 朝向约定一致。
- 不误用候选图作为正式资源。
- 贴图过滤和压缩符合像素/写实风格约定。
- 特效颜色与敌我语义一致。
- 普通攻击和 Boss 大招的视觉层级有明显差异。

## 4. 内容校验管线

每次编辑器运行、自动测试或正式构建前检查：

### 4.1 通用校验

- ID 格式合法且唯一。
- 引用目标存在且类型正确。
- 内容包依赖满足。
- 本地化 Key 存在。
- PackedScene 和资源路径可加载。

### 4.2 技能与 Modifier

- 时间、范围、速度和资源消耗非负。
- Tick 间隔大于零。
- 投射物和区域有寿命或销毁条件。
- HitGroupId 合法。
- 效果 Handler 已注册。
- 持续效果存在明确叠加和驱散规则。
- 技能使用的 Cue 存在。

### 4.3 地图

- EntranceId、ActorId、PersistentId 在地图内唯一。
- 出口目标存在。
- Encounter 和 Quest 引用存在。
- 关键入口有出生位置和朝向。
- 快速旅行入口符合标签约定。

### 4.4 任务

- 前置任务存在。
- 任务依赖无环。
- 目标类型有运行时 Handler。
- 奖励内容存在。
- 发布后修改任务结构时有迁移策略。

## 5. 测试分层

### 5.1 纯 C# 规则测试

测试内容：

- 伤害公式。
- 暴击和方向减伤。
- Buff 叠加与权限聚合。
- 冷却和资源事务。
- 任务条件。
- 存档迁移。
- 确定性随机结果。

优点是快速、稳定，不依赖完整场景。

### 5.2 Godot 场景集成测试

测试内容：

- Hitbox 与 Hurtbox。
- 突进撞墙。
- 快速投射物命中。
- 动画桥接。
- 场景切换清理。
- 地图入口定位。
- 暂停和重开。

现有 `Scripts/Tests/CombatSmokeTests.cs` 可以作为这一层的起点。

### 5.3 内容冒烟测试

自动遍历：

- 每个 SkillDefinition 能否构造运行时实例。
- 每个 UnitDefinition 能否生成场景。
- 每张地图能否加载并找到全部入口。
- 每个 QuestDefinition 能否建立目标图。
- 每个 Cue 能否加载对应资源。

### 5.4 手工体验测试

自动测试不能代替：

- 打击感。
- 技能辨识度。
- Boss 前摇是否公平。
- 地图是否迷路。
- 特效是否遮挡角色和危险提示。
- 键鼠和手柄操作舒适度。

## 6. 可观测性和调试工具

调试包建议提供：

- 当前单位状态、权限和 Modifier 列表。
- 技能阶段、CastId、HitGroupId 和 CD。
- Hitbox、Hurtbox、导航和地图 Trigger 显示。
- 最近若干 DamageRequest/Result。
- 事件队列深度和触发预算。
- 当前 MapId、EntranceId、EncounterId、Quest 状态。
- 内容包和存档版本。
- Cue 并发数量和对象池状态。

日志使用结构化字段，避免只能看到“技能失败”而不知道是资源、权限、目标、CD 还是场景清理造成。

## 7. 随机数和复现

暴击、多重施法、AI 随机选择等统一通过可注入的 RNG 服务：

- 每场遭遇记录 Seed。
- 战斗日志记录关键随机决策。
- 自动测试使用固定 Seed。
- 表现粒子的随机数与规则随机数分开。

这样才能复现“偶尔多重施法无限触发”或“特定情况下 Boss 不行动”等问题。

## 8. 构建管线

```text
C# 构建
→ 内容校验
→ 规则测试
→ 场景冒烟测试
→ 缺失本地化检查
→ 导出 PCK/可执行文件
→ 安装包冒烟测试
→ 生成版本与内容清单
→ 保留构建和迁移记录
```

正式构建需要记录：

- GameVersion。
- Commit 或源码版本标识。
- SaveVersion。
- Content Pack 版本和 Hash。
- Godot 版本。
- 目标平台。
- 已知问题。

## 9. 分阶段演进路线

### 阶段一：保持当前对战可玩

- 完成吕布与魏延的完整胜负、重开和基本手感。
- 保留现有 CombatSmokeTests。
- 不进行全工程重写。

### 阶段二：抽取技能与状态内核

- 从普攻、横扫、突进中提取 SkillDefinition、SkillRuntime 和 SkillCast。
- 建立 ContentRegistry 和稳定 ID。
- 引入 DamageResolver 和最小 ModifierContainer。
- 建立 SkillSandbox 和内容校验器。

### 阶段三：验证四类关键机制

至少实现：

- 方向近战技能。
- 突进或位移技能。
- 龙卷风式移动持续区域。
- 光环或持续 Buff。

四类机制能覆盖大量后续技能组合。

### 阶段四：建立短冒险闭环

- 一座起始村。
- 一张野外地图。
- 一个地标或洞窟。
- 一个 Boss 房。
- 技能习得、配置、任务、存读档和返回营地。

### 阶段五：精致垂直切片

- 补齐正式动画、刀光、光环、音效和镜头。
- 根据 20–30 分钟试玩验证制作速度和模块边界。
- 冻结首发内容上限。

### 阶段六：内容生产和发布

- 批量制作技能、敌人、地图和任务。
- 完善多语言、手柄、可用性和 Steam 接入。
- 建立正式构建、备份和存档迁移流程。

### 阶段七：DLC

- 使用命名空间和 Content Pack 增加章节。
- 平台层验证所有权。
- 核心流程通过内容注册发现入口。
- 每个 DLC 单独验证存档兼容和卸载后的行为。

## 10. 架构演进规则

1. 有两到三个真实重复案例后再抽象。
2. 一个架构调整必须说明解决的具体制作或运行问题。
3. 抽象后不能降低当前阶段的可玩性和可验证性。
4. 优先增加校验、调试和沙盒能力，再增加复杂编辑器。
5. 通过新增技能、地图和任务的平均耗时衡量扩展性。
6. 性能优化以分析数据为依据，不提前为假设瓶颈制造复杂度。
7. 文档中的目标结构与当前实现要持续区分。

## 11. 最终验收指标

当项目达到较成熟阶段时，架构应满足：

- 80% 普通技能由已有积木配置完成。
- 20% 特殊技能通过独立 Handler 扩展，不侵入核心。
- 新敌人复用 Actor、Command、Ability、Combat 和 Modifier。
- 新地图通过 Definition、场景和入口注册接入。
- 新任务通过语义事件推进，不修改地图核心脚本。
- VFX 和音频可替换，不改变战斗结果。
- 内容错误在构建或加载期暴露，而不是玩家游玩到中途才出现。
- 新 DLC 可以独立启停，并有明确存档兼容策略。
