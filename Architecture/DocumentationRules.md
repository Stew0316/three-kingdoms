# 架构与游戏内容的文档边界

日期：2026-10-24。状态：用户明确确认的长期规则。

## 归类原则

`Architecture` 保存独立于具体游戏内容的系统设计：机制、不变量、模块职责、数据所有权、生命周期、接口、扩展方式及通用制作验证方法。玩法系统设计也属于架构，例如技能分类、技能树、习得/培养/配装、目标资格和组合约束。

具体人物、某个招式的数值、某张地图、任务与奖励、城池布局、故事对白、资产版本、界面摆放、迭代过程和验收结果不放入 `Architecture`。

判定问题：换掉人物、城池、关卡与素材后，这段规则是否仍然成立？成立的系统规则归架构；必须依靠具体对象和参数才能描述的实例归内容。现有类名和资源入口可以用于定位系统实现，不代表对应内容参数也应抄入架构。

## 文档落点

| 位置 | 职责 |
| --- | --- |
| `Architecture` | 通用系统设计、当前系统边界、技术决策及扩展合同 |
| `Demand/Content` | 当前具体内容、内容配置说明、场景/人物实现索引 |
| `Demand/Content/Records` | 本次迁出的历史混合文档；保留证据，不继续作为现行规范维护 |
| `Demand/Design` | 具体玩法设想、招式样例、遭遇和世界构想，标明提案/已实现 |
| `Demand/Prompt` | 用户原始需求、当次决定、整理过程与验收摘要 |
| `Demand/Stage` | 制作顺序、阶段范围、交付目标、验收计划 |
| `Demand/美术` | 资产生成、采样标定、版本及美术验证 |
| `Drama` | 故事、人物小传、章节、城池剧情和对白 |
| `Resources` / `Scene` / `Source` | 引擎配置实例、实际场景和源资产；不是架构说明的替代品 |
| `Build` | 构建、检查脚本的临时输出、截图与日志 |

## 混合文档拆分

同一需求同时涉及系统和内容时，拆成两个文档并互链，不用一个含两个主题的架构文件长期承载。

| 主题 | 架构保留 | 内容或记录迁出 |
| --- | --- | --- |
| 启动与外景 | 异步加载、首帧覆盖、失败反馈、路由与清理 | 启动文案与 Logo 排版、某座山的原画、路径、入口坐标 |
| 地图与任务 | 稳定入口、持久状态、任务推进与幂等奖励 | 某城有哪些 NPC、任务目标、训练收益与地图路线 |
| 角色与动作 | 模型/动作/技能分离、采样接口与时钟 | 某武将的握距、姿态角度、贴图版本和裁切窗口 |
| 技能体系 | 树分类、目标性质、状态规则、触发限制 | 某将装备哪四招、技能数值、解锁地点、具体 Boss 配合 |
| UI 与昼夜 | 输入映射、暂停所有权、时间源、数据读取 | 玉玺摆放、钟盘大小、默认纪年、图标版本和截图 |

抽象结构示意可以使用匿名字段和占位 ID，但不在架构中展开可直接当作正式内容配置的完整招式或关卡。具体样例链接到 `Demand/Design` 或 `Demand/Content`。

## 状态与维护

- 清楚区分已确认设计、提案、现有实现和已验收；设计确认不等于代码已实现。
- 架构文档描述现行规则和目标差异，不持续追加逐日变更日志。历史过程放 `Demand`，架构只保留必要原因与来源链接。
- 系统实现索引与内容实现索引分别维护；具体数值以资源为源，文档不制造第二份配置源。
- 迁移保留必要历史证据，更新相对链接、根阅读入口和阶段文档入口；删除失效旧入口前检查所有引用。
- 优先使用已有一级目录，不为文档分类新增根目录，也不为统一名字无依据搬动 Godot 场景、UID、资源或子模块。
- 新增英文目录与文件使用 PascalCase；既有编号中文架构文档延续原系列命名。存档 ID 与已引用资源名不因文档整理批量改名。
