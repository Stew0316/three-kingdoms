## 1. 文档目的

本目录记录《吕布游历》的长期架构方向，重点解决以下问题：

- 如何用 Godot 4.7.1 C# 制作以实时对战和游历为核心的 2D 单机 RPG。
- 如何借鉴 Dota 2 的技能与 Modifier 组合能力、Warcraft III 的对象与触发器编辑思路。
- 如何借鉴《宝可梦 火红/叶绿》的地图连接和重访结构，以及《魔女之泉》的据点、外出、训练与成长循环。
- 如何让技能、敌人、地图、任务、特效和 DLC 能以内容形式扩展，而不是持续修改核心代码。
- 如何建立适合小团队的制作、校验、测试和发布管线。

架构目标不是复制 Dota 2 或 Warcraft III 的完整编辑器，而是保留最有价值的部分：**稳定规则、数据驱动、组合式能力、表现解耦、内容校验和可追踪的运行时状态**。

## 3. 与现有阶段文档的关系

本目录描述长期结构；`Demand/Stage` 描述当前项目应该按什么顺序交付。两者分工如下：

- `Architecture/`：定义目标结构、模块边界和长期不变量。
- `Demand/Stage/`：定义阶段范围、任务、验收条件和工时边界。
- `Demand/Design/`：保存玩法、剧情、美术和世界观想法。
- `Demand/Prompt/`：保存用户提出的原始问题和上下文。

已有文档中，[战斗与扩展架构](../Demand/Stage/附录-战斗与扩展架构.md)和[S2：技能与状态内核](../Demand/Stage/S2-技能与状态内核.md)仍然有效。本目录在其基础上补充整局游戏模块、地图、表现、内容包和生产管线，不取代已经写明的阶段交付顺序。

## 4. 文档状态约定

后续细化时，每个设计项应标记为以下状态之一：

| 状态 | 含义 |
| --- | --- |
| 提案 | 有方向但尚未通过实际内容验证 |
| 已确认 | 已由需求或试玩确认 |
| 实现中 | 当前阶段正在落地 |
| 已实现 | 已存在代码和基本测试 |
| 已验收 | 已通过对应阶段的验收标准 |
| 延期 | 保留方向，但不进入当前版本 |

文档中出现的类名、目录和接口，如果没有“已实现”标记，都只代表建议结构。

## 5. 核心验收标准

架构是否真正具备扩展性，最终看以下结果，而不是看类和接口的数量：

1. 使用已有机制制作普通新技能时，只增加 Definition、表现资源和角色配置，不修改战斗核心。
2. 一个新技能最多引入一个未验证的底层机制；特殊机制通过独立 Handler 扩展。
3. 玩家、Boss 和小兵通过同一命令、技能、伤害与状态入口行动。
4. 新地图通过 `MapDefinition` 和稳定入口 ID 接入，不在全局流程中增加地图名称判断。
5. 任务只读取语义事件，不直接依赖具体地图节点路径。
6. 特效缺失或播放失败不能影响伤害、Buff、冷却和胜负结算。
7. 存档保存稳定 ID 和普通数据，不保存 Node、Delegate、运行中的 Task 或场景路径引用。
8. 新内容包使用独立命名空间，核心代码中不出现散落的 DLC 条件判断。
