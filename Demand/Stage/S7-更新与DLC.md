# S7：在完整本体上扩展内容

前置：本体发布稳定，玩家反馈与制作能力支持扩展。没有固定开工日期；不把本阶段加入首发倒计时。

## 先修体验，再选一项扩展

优先处理崩溃、存档、操作、文本与影响战斗判断的问题，再评估新区域、技能、三仙支线或小型挑战。一个更新只验证一个主要新机制，避免同时加入多周目、偷技能、骑乘战斗与双路线剧情。

首个 DLC 可提案为“于吉异闻”一类独立短篇：1 段新的探索区域、1 名人形 Boss、2 个玩家版技能、一个短结局；复用吕布动作、地块和传送系统。这个名字与规格仅为设计例，不是已确认销售计划。本体的主要故事与左慈基础传送在购买 DLC 前就完整可用。

## 早期预埋与此时实现的区别

| 早期已经规划的基础 | S7 才需要的完整能力 |
| --- | --- |
| `core` 内容包标识、稳定技能/地图/任务 ID | 一个具体扩展包的素材、任务、技能和地图注册 |
| 版本化存档和未知 ID 的保留 | 安装/卸载 DLC 后的迁移与恢复验证 |
| 离线平台边界 | Steam 所有权/安装状态与游戏内容可用性映射 |
| 数据定义与执行器分离 | 新内容复用既有执行器；新增代码随本体更新 |
| 安全点与左慈传送锚点 ID | 新区域完成首次到访后加入同一传送列表 |

每个内容包清单至少包含 `packId`、`version`、所需本体版本、依赖、入口地图、内容 ID 列表与本地化资源。加载前校验重复 ID、缺依赖和版本不兼容；不允许扩展包悄悄覆盖 `core` 定义。

采用数据与资源驱动的内容包即可。PCK/安装目录等介质按发布方案验证；C# 新玩法代码随本体兼容更新，不把普通资源包误当作可以任意加载新程序集的 mod 框架。

Steam DLC 有独立 AppID，内容可以随本体提供并按权限开放，也可以使用独立 depot；因此“拥有内容”与“本机内容可用”需要分别判断。[Steam DLC 官方说明](https://partner.steamgames.com/doc/store/application/dlc)

## 缺失 DLC 时怎样保护玩家

| 状态 | 行为 |
| --- | --- |
| 未拥有或未安装 | 不开放入口；提示原因，不把未购买当成存档损坏 |
| 当前档位于 DLC 地图 | 提示缺失包，保留原档，可加载安全恢复副本回本体驿站 |
| 吕布装备 DLC 技能 | 暂时禁用缺失槽，填入已拥有的本体技能或留空；保留原始装备记录 |
| DLC 任务/强化/坐骑数据 | 暂停使用但原数据保留，安装恢复后重新校验 |
| DLC 左慈锚点不可用 | 从可选目的地隐藏/标不可用；不能传送到空地图 |
| 版本过新或依赖错误 | 给明确错误，不写回破坏性降级存档 |

任何恢复先做备份，不覆盖唯一含完整 DLC 进度的原始档。恢复副本与原档有独立槽 ID，避免云同步把恢复操作当作原档被清空。

## 候选内容的进入条件

- 多重施法：先做一次特定技能的受控二重版本，证明事件链、CD 和反馈可读；不全局随机无限复制。
- 偷技能：仅允许有标签、已制作玩家版的招式白名单；必须补充交互、提示和每个技能的取消/保存验证。
- 新坐骑：复用已有赶路规则，用获得经历与外观区分；不默认扩成育种、马战和装备树。
- 三仙长支线：本体短支线反馈良好、对白/地图预算明确后再扩；不牵连整个主线重写。
- 攻城、雪山、海岛、双路线：各是独立内容立项，不能以“已有接口”视为低成本。

用户已明确当前不做多人或 PvP，本路线不排网络开发。未来改变这一条件，需要新的玩法与技术评估，不能把 Steam 接入或命令接口当作联机已准备好。

## 验收与交付

- [ ] 不装 DLC 可以完整通关本体；装 DLC 后可从既有档进入新内容。
- [ ] 安装、卸载、重新安装、版本不匹配和平台离线有确定结果，原始进度可恢复。
- [ ] DLC 技能、奖励、地图与传送点都有唯一 ID；未知数据保留，奖励不重发。
- [ ] 新内容使用既有四语流程与风格版本，性能和低特效可读性没有倒退。
- [ ] 回归本体主线与至少两份旧档，更新包、兼容说明与回退限制同时交付。

上线后是否收费、何时发布以及实际 DLC 规模，应在本阶段依据内容量与玩家反馈重新决定。
